# Phase 2A domain implementation report

Scope: the approved domain/state-machine milestone only. Phase 2 as a whole is not complete.

## Implemented

- Strict Pydantic address/patch schemas with nine nullable strings, length limits and control-character rejection. Explicit null clears; omission preserves; empty patches fail. PIN candidates remain strings and can be incomplete pending validation. A VALID canonical result requires six ASCII digits.
- Immutable address snapshots and session aggregates. Changed patches increment the version, preserve unaffected fields and clear validation/read-back/confirmation. Identical updates are no-ops. Stale updates and stale validation results fail without mutating the original aggregate.
- Bound validation attempts with immutable history. Revalidating the same version revokes consent. Duplicate identical validation results do not resurrect earlier eligibility. Changed canonical data requires a versioned update instead of silent normalization.
- Deterministic full English read-back text and SHA-256 digest. Each attempt binds the exact address version and validation attempt. Preparing text is not playback completion.
- A fail-closed evidence verifier interface. Completion and confirmation evidence must match session, execution, version, validation attempt, read-back attempt and text digest. Confirmation must be subsequent in the evidence source's ordered stream. Duplicates are idempotent only for the same accepted event; reused IDs and wrong bindings fail.
- Independent save eligibility checks and an internal saved-receipt hook. The guard enforces positive current=validated=confirmed versions plus valid read-back/confirmation evidence. Corrections and interruption revoke current acceptance while retaining historical saved references.
- Safe audit events containing operation/version/reference IDs and reason codes, without duplicating customer address values.

## Trust boundary and limits

This is an internal domain library, not an authenticated service. Production application code is trusted to supply sessions from its repository, validation results from its validator and evidence from an independently authenticated adapter. Python object types do not authenticate data, and frozen models are not a sandbox against hostile code running in the same process. Never deserialize an LLM-provided Session or VerifiedEvidence directly into a trusted service operation.

The default verifier rejects all references. The only synthetic verifier is in tests/unit/conftest.py and is excluded from the application package. There is no test-mode flag, development confirmation endpoint, trusted=true input, or permissive fallback. A future adapter must resolve provenance and bind evidence to the actual playback/customer response. Source sequence numbers must be monotonic for the linked execution; they are not independently generated by the LLM.

No real validation engine or evidence source is connected. Schema constraints and six-digit format do not establish geographical correctness, address completeness, or real customer consent. In 2B the validator must establish required fields and PIN/location consistency. The read-back renderer is English only at this milestone; production multilingual rendering and audio evidence must use the exact corresponding text/digest.

`record_saved` records an in-memory receipt supplied by trusted repository code; it does not perform or prove a database commit. Later PostgreSQL transactions must atomically enforce optimistic concurrency, unique session/version saves, and supersession of the previously accepted address. This domain library alone does not prevent parallel processes from overwriting each other.

Address versions, validation results and read-back text contain PII. They must not be logged as whole objects. Rendered schema errors hide input values, but structured Pydantic error details can still include input if a caller explicitly requests them; future API error serialization must redact those details. Audit events intentionally omit address values.
