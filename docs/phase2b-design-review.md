# Phase 2B design review

Reviewed against the current Phase 2A domain implementation. The submitted proposal is preserved in phase2b-proposed-design.txt. This is a design review, not implementation or approval of a production dataset.

The proposed scope and conservative postal matching are sound. Resolve the following before implementation.

1. **Separate engine outcomes from domain validation status.** Sections 7 and 54 differ about a fourth status. Keep the three existing domain statuses. Return an engine-level union: a normalization proposal OR a domain validation result. A proposal must never grant validation eligibility.
2. **Preserve raw values and field origins through normalization.** Existing update_candidate patches both raw and canonical addresses. Calling it with a normalized PIN would overwrite the customer representation. Add a dedicated expected-version normalization transition that preserves raw, appends a canonical snapshot, records immutable field origins and proposal provenance, and revokes validation/read-back/confirmation/current save eligibility. Later customer corrections must remove or recompute dependent postal-derived fields, especially state when PIN changes; retained derivations must not masquerade as customer claims.
3. **Keep rich evidence in immutable validation history.** Extend or compose the existing ValidationResult rather than create an incompatible parallel result. Keep attempt_id, exact version binding, canonical equality checks, immutable reasons/conflicts/warnings, policy version, field origins and dataset provenance. Duplicate-attempt comparison must include this evidence. Normalization proposals also need exact base snapshot binding and stale-proposal rejection.
4. **Define the premise policy precisely.** A nonblank building alone can describe a shared apartment complex. Recommend requiring house_flat by default, or an explicit customer-supplied premise description under a named deterministic policy; never claim string length establishes deliverability. Decide how the alternative is represented in the existing nine-field schema before coding. A landmark alone should not automatically satisfy premise identification.
5. **Define ambiguity and freshness behavior.** Recommend VALIDATION_ERROR for contradictory authoritative states, missing provenance, corruption and expired datasets; NEEDS_CLARIFICATION for customer omissions, malformed/unknown PIN and strong customer/reference conflicts. Specify a configurable maximum source age and injected evaluation date; import time cannot reset source freshness. Multiple districts are legitimate: a supplied district matching any supported option passes. Missing district evidence is uncertainty, not a conflict.
6. **Separate integrity from authenticity.** A computed SHA-256 establishes file identity, not official origin. Record official resource URL/identifier, source release date, import time, original download hash and normalized artifact hash. Import only through an explicitly trusted operator workflow. Fail on malformed rows without partial readiness; synthetic fixtures must be identified as synthetic and never selected as the runtime directory.
7. **Bound PIN normalization.** Recommend Unicode decimal conversion and an explicit spacing allowlist; reject letters, superscripts, zero-width characters and punctuation not specifically permitted. Do not apply broad compatibility normalization before decimal checks. Normalization must be idempotent and preserve the original customer text.

## Official source check

The [OGD catalog](https://data.gov.in/catalog/all-india-pincode-directory-through-webservice) identifies Department of Posts, lists the postal hierarchy fields, and states monthly updates. The catalog resource entry reports 10/08/2026 while the separately indexed resource page reports an older update. Record the date on the actual acquired release; do not substitute a site-footer timestamp or assume a monthly schedule proves freshness. No official dataset has been acquired or ingestion-tested in this review.

## Recommended implementation boundary

Keep the local immutable directory and pure validator proposed by the user. Add only the domain normalization/provenance changes necessary to preserve 2A guarantees. Keep database, HTTP, voice, deployment and automatic refresh outside 2B. Test synthetic cases separately from real official-file ingestion and report their test_result independently; unexecuted ingestion/live checks remain NOT_RUN.
